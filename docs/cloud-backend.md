# Cloud patch backend

The application remains a static synthesizer. The single Vercel Web Handler in `api/index.js` delegates `/api/*`, saved patch pages and their images to `server/handler.js`. The production handler never selects an in-memory database or a fixture identity. Without configuration, `/api/config` returns `enabled: false` and protected routes return an actionable 503; local patches and embedded snapshot links remain available.

## Authentication decision

Use self-hosted Better Auth on the application's Vercel origin with Google OAuth, backed by Neon PostgreSQL. Its `pg.Pool` adapter, Fetch handler and database-backed rate limiter are supported by the pinned installed package. Same-origin secure cookies avoid the separate auth-domain cookie dependency. Sessions are checked against the database on API calls, with no browser-readable JWT or cookie-session cache. Application mutations require the exact application Origin. Google and Better Auth own the OAuth state/PKCE/callback flow. [Better Auth PostgreSQL adapter](https://better-auth.com/docs/adapters/postgresql), [Better Auth installation](https://better-auth.com/docs/installation).

`api/index.js` uses the documented `export default { fetch }` format. Rewrites forward `/api/:path*` to `/api?__path=/api/:path*`, `/patches/:id` to `/api?__path=/patches/:id`, and `/patches/:id/images/:previewId/:variant` to `/api?__path=/patches/:id/images/:previewId/:variant`. The entry point restores that route only if the runtime exposes the rewritten `/api` destination; otherwise it retains the original pathname. `/patches` is the static gallery. [Vercel Node runtime](https://vercel.com/docs/functions/runtimes/node-js), [Vercel rewrites](https://vercel.com/docs/routing/rewrites).

The existing Vercel project is connected to Neon with a separate preview database. Its integration currently supplies `DATABASE_URL`; `STORAGE_URL` is also accepted after PostgreSQL URL validation. Image storage uses **private Vercel Blob**, with separate preview and production stores connected. The Vercel preview migration and real Blob upload/download/delete check passed. Google credentials and a deployed redirect/login/logout test in Chromium and WebKit remain pending. See [setup and deployment status](cloud-setup.md).

## Server environment

| Variable | Meaning |
| --- | --- |
| `DATABASE_URL` or `STORAGE_URL` | Neon Postgres connection string, including its required TLS parameters; server only. `DATABASE_URL` takes precedence. Only `postgres:`/`postgresql:` URLs are accepted. |
| `BETTER_AUTH_URL` | Exact application origin, for example `https://your-domain.example`; no path. `APP_URL` is an accepted fallback. |
| `BETTER_AUTH_SECRET` | High-entropy secret of at least 32 characters; server only. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google web OAuth application credentials. |
| `BLOB_READ_WRITE_TOKEN` | Server-only read/write token for the connected **private** Vercel Blob store. Takes priority over optional S3 configuration. Never include it in browser bundles or public configuration. |

Google's authorized redirect URI is `<BETTER_AUTH_URL>/api/auth/callback/google`. Use separate credentials/database/bucket for development and preview deployments, with exact origins; never wildcard trust arbitrary preview domains. Vercel production must use HTTPS. No secret belongs in `dist`, public config, git, or a patch URL.

Run `node --env-file=.env.local db/migrate.mjs` with a migration-capable database credential. Only the database connection is needed to prepare the schema; Google provisioning can follow. This applies the installed Better Auth version's own schema through its migration API, then the idempotent patch schema in `db/001-patches.sql`. Use a restricted runtime database role with access only to the auth and patch tables; the anonymous Neon/Data API role must not have access. Back up before applying future schema changes.

Run `node --env-file=.env.local db/cleanup.mjs` periodically (for example daily through your existing job runner). It atomically removes unattached preview associations older than 24 hours and enqueues their unreferenced bytes in `patch_image_garbage`, then attempts object deletions outside the database transaction. Failed deletions remain queued for a later run. Shared image bytes remain until every fork's association releases them. Failed uploads also enqueue attempted keys when the database is reachable. This command is intentionally not an unauthenticated HTTP endpoint. Newly uploaded images remain private while a save is pending. Deleted previews disappear from HTTP immediately even before storage cleanup.

Create a private Blob store in the existing Vercel project's Storage tab and connect it to the intended environments with `BLOB_READ_WRITE_TOKEN`. Use separate stores for Production and Preview/Development so preview cleanup cannot delete production images. The equivalent CLI command is `vercel blob create-store eurorack-patches-preview --access private --environment preview --environment development`; create a separate production store with `--environment production`. Pull the selected environment into an ignored local env file without printing its values. The SDK and CLI support private stores; this application explicitly passes the server token and private access for uploads/downloads. [Vercel private storage](https://vercel.com/docs/vercel-blob/private-storage).

The Blob adapter was checked against the pinned `@vercel/blob` **2.8.2** source and types. It keeps deterministic ULID paths, disables random suffixes and overwrites, and reads with `useCache: false`. Provider paths/URLs and credentials never enter API projections. Application image responses remain visibility-gated and `no-store`; the provider's minimum upload cache setting is 60 seconds and applies behind authenticated Blob access. Garbage-queue cleanup uses idempotent Blob deletions. [Vercel Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk).

Vercel Blob stores do not automatically follow Neon database branches. If a future preview database is seeded from populated production data, seed corresponding preview images separately; do not point preview cleanup at the production Blob store.

The previously implemented S3-compatible adapter remains optional when no Blob token is configured. It accepts `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION`, optional `S3_SESSION_TOKEN` and `S3_FORCE_PATH_STYLE`. Corresponding `AWS_ENDPOINT_URL_S3`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`/`AWS_DEFAULT_REGION` and `AWS_SESSION_TOKEN` aliases are supported; `S3_BUCKET` remains explicit. The AWS endpoint alias defaults to path-style addressing. Production endpoints must use HTTPS. The chosen deployment uses Blob and does not need these variables.

## API and persistence contract

`createHandler({store, authenticate, imageStore, baseUrl})` accepts a standard Fetch Request and returns a Response. `createPatchService()` provides the same domain operations without HTTP. The Postgres adapter uses short transactions plus an advisory lock to serialize writes, quotas, likes and visibility. This intentionally favors a small application's correctness; before substantial traffic, use ordered per-owner/per-record locks and batched catalogue reaction aggregation.

Records store exact v3 JSON and generated SHA-256 state fingerprints. ULIDs identify patches, pending images and create requests. Owner subjects never come from JSON or appear in public projections. All owner edits require `expectedRevision`; content saves and visibility updates increment revision, likes do not. New and copied records are idempotent by owner/request ULID plus request fingerprint, and retain a request tombstone on deletion so delayed retries cannot recreate removed content.

`GET /api/public-patches?q=&sort=&period=&cursor=&limit=` lists public summaries; `GET /api/patches?q=&cursor=&limit=` lists the signed-in user's summaries. Pages contain 24 entries by default (maximum 50) and return opaque `nextCursor` and `previousCursor` values, either of which goes in the next request's `cursor` parameter. Cursors use exclusive ranking boundaries, not offsets, and are bound to the search, sorting, time period, account scope and page size. Summaries omit patch state and include module count, creator credit and image URLs. Search is bounded, case-insensitive literal substring matching over name, description and creator name.

Public lists support `sort=newest` (default, descending creation ULID) and `sort=popular` (descending thumbs-ups, then descending ULID). Popularity uses `period=all|day|week|month|year`, counting current reactions received in all time or the preceding 24 hours, 7 days, 30 days or 365 days. A repeated like preserves its original timestamp. `popularityCount` reports the selected period's score; `likeCount` remains the total. Cursors hold the first page's timestamp so new patches and later likes do not move into that traversal. Unlikes, deletions and privacy changes still affect subsequent pages; visibility is checked on every request. The idempotent migration adds a `(patch_id, created_at)` likes index for these lookups.

Catalogue navigation is URL-driven: `/patches` is Public patches, `?view=tests` is Test patches, and `?view=mine` is My patches. The address carries `q`, public `sort`/`period`, and the page `cursor`; the browser-saved section of My patches uses a separate `localCursor`. Test patches and browser saves also use 24-entry cursor pages. Search and filter changes clear cursors. Previous/Next links, reloads and browser Back/Forward restore the requested page, and opening a rack preserves its catalogue entry in browser history.

`POST /api/patch-previews` accepts multipart `image`, exact JSON `state`, optional `rendererVersion` and `theme`; returns `{id,stateHash}`. PNG/JPEG/WebP inputs are decoded, stripped of metadata and re-encoded as PNG. Variants are `thumbnail`, `full`, and 1200×630 `social`; all contain only the supplied rack raster. The backend verifies content format and matching state hash; it cannot prove visually that a user's uploaded raster depicts their modules. The official client generates that raster from the captured exact rack state.

`POST /api/patches` accepts `{requestId,name,description,authorName,state,visibility,previewId}`. A public save requires a matching ready image. `PUT /api/patches/:id` accepts the same editable fields with `expectedRevision` instead of `requestId` and retains visibility unless explicitly changed. An owner may update their display name for that record; existing original-creator and parent-credit snapshots remain immutable. `PUT /api/patches/:id/visibility` accepts `{expectedRevision,visibility}`. A private toggle never needs a fresh image. `DELETE /api/patches/:id` accepts `{expectedRevision}`.

`POST /api/patches/:id/copies` accepts `{requestId,expectedRevision,name,authorName,state?,previewId?}`. Omit state to copy the saved source; include state to fork an edited editor snapshot. Every fork starts private, including a caller's own copy, and a later explicit content save is required before publication. Server-derived immediate parent, parent revision, root and original creator snapshots survive source deletion/privacy changes. A state-identical copy gets its own preview association with reference-aware cleanup. Forks start with zero thumbs-up.

`PUT /api/patches/:id/like` accepts `{liked:boolean}` and changes one reaction for another user's public patch. Copies, likes, API reads, HTML and image routes check current visibility. Owner sessions may fetch private images; anonymous/private failures are indistinguishable from missing records. Response headers prohibit browser, CDN and Vercel response caching. Third-party social previews or previously downloaded copies cannot be recalled by later privacy changes.

Public `/patches/:id` HTML has initial Open Graph/Twitter metadata with a canonical saved URL and rack-only PNG. Private or missing pages always emit a generic noindex shell, even for an owner; the browser then fetches private data with its session. Text is escaped and HTML has a restrictive content security policy. The existing `#patch=` embedded snapshot URL is independent.

The canonical `/patches/:id` URL opens directly in the rack, including on refresh. Saving or opening an account patch also sets that address; legacy `#saved=` and `?view=rack` links normalize to it. The optional Details view uses `?view=details` for description, creator credit and social actions. Both server HTML views use the same anonymous-only metadata, with social descriptions limited to 200 characters. Public images permit cross-origin embeds and anonymous CORS reads; private images retain same-origin CORP and no CORS permission. GET and HEAD recheck image access after object retrieval and remain uncached.

## Limits and verification

The cloud boundary validates the existing v3 schema against static module metadata without instantiating DSP. It rejects unknown modules/plugins/parameters, unsafe keys, invalid endpoint directions, duplicate destinations, unsafe instance IDs, invalid placements, rows over 84 HP, numeric control values outside their declared ranges, invalid MIDI mappings and nonfinite/deep structures. Limits: 256 KiB state, 256 modules, 2,048 cables, 32 rows, 100 patches/10 MiB state per account; images allow 2 MiB uploads, 8 million decoded pixels, 1 MiB derived variants and 50 MiB per account. Limits apply only to cloud storage, never silently truncate a local rack.

`npm test -- tests/server` verifies the real handler/service with a transactional in-memory adapter and real Sharp image decoding. Tests cover privacy revocation across JSON/HTML/images/copies, ownership, revision races, idempotency, fork lineage and save gate, raster/state mismatches, cleanup references, reactions, pagination, CSRF, quotas and limits. A fixture harness is available at `tests/server/test-backend.js`; it requires `NODE_ENV=test`, refuses Vercel and is never imported by production. It may use local filesystem images for explicit local integration.

The three optional PostgreSQL integration tests were exercised against a disposable local Postgres 18 container: the actual pinned Better Auth migration, forged-session rejection, cross-origin auth rejection, Google authorization-state initialization, and real SQL patch/image/fork/reaction/revision/idempotency operations passed. To repeat, set `TEST_DATABASE_URL` to a local database named `eurorack_test` and run `npm test -- tests/server/postgres.integration.test.js`; other hosts/database names are refused. The default test run skips those three integration cases without this explicit variable.

A live Neon connection, private Blob permissions and the complete Google callback/refresh/logout flow must still be exercised in the deployment environment. Unit and local browser coverage do not substitute for that deployment check.
